# 我用 LangGraph 给教务系统做了个 Agent，踩了五个坑

> ## 三分钟口播版（要讲的时候念这段）
>
> 我做的是一个智能教务系统。起因很土：我们学校查一次成绩要点五层菜单。
> 所以我把系统里每个功能都拆成一个函数，让大模型当点菜单的人——学生说「我上学期高数多少分」，它自己选工具、自己抽参数、自己查。
> 用 LangGraph 没用一行封装，是因为我要工具循环、失败重试、人工确认、链路记录这四件事。
> 跑起来之后踩了五个坑：提示词里裸拼接把布尔值拼成了 deepseek-chatfalse；把数据库会话塞进 State，checkpoint 直接序列化失败；模型把「周三」抽成字符串，工具就炸；聊十轮之后历史越堆越慢；前端请求漏写 method，全报 405。
> 最值钱的一条经验是：Agent 的 bug 大多不是崩溃，是流程成功但答案是错的——所以参数要收敛，查不到要回退。
> 现在这套系统三种身份、两套模型两套工具清单，越权不是靠提示词拦，是那个工具压根不在它手里。
> 仓库在下面，欢迎来看。

> 先说结论：一个能跑的 Agent 不难，难的是让它**在真实业务里不胡说、不越权、不越跑越慢**。
> 这篇把我做「智能教务系统」时踩过的五个坑按顺序讲一遍，每个坑都给现象、原因、最后怎么解决的。代码是 Python + FastAPI + LangGraph，仓库在文末。

## 起因：为什么一个教务系统需要 Agent

事情是从一个很土的场景开始的。

我们学校查一次成绩要点五层菜单：成绩查询 → 选学期 → 选课程 → 输姓名 → 查询。一个数字，五步操作。
老师那边更夸张，想在后台给某个班发一条调课通知，得先找到班级、再找到课程、再勾人、再写通知。

所以我想做的事很简单：**把系统里每个功能都拆成一个能被程序调用的函数，然后让大模型当那个「点菜单的人」。**
学生说「我上学期高数多少分」，模型自己去判断该调 `query_grades`，自己抽参数，自己去查。

技术上就是 LangChain 管模型和工具、LangGraph 管流程。之所以没直接用 `create_agent` 那种一行搞定的高层封装，是因为我需要四件事：多轮的工具循环、出错能重试、中间能停下来等人工确认、每一轮发生过什么能被记录。这四件恰好是「有状态的图」擅长、而「一条链」不擅长的。

流程被切成四个节点：**理解需求 → 规划工具 → 执行工具 → 组织回答**。听起来很顺，坑就从这里开始。

## 坑一：模型名字显示成了 `deepseek-chatfalse`

**现象**：界面上那行小字显示「模型：deepseek-chatfalse」，多出来的 `false` 像是被人拼上去的。

**原因**：我在提示词模板里用了字符串拼接，大概长这样：

```python
prompt = "你是学生的教务助手，学生姓名：" + name + "，当前是否离线：" + offline
```

`offline` 是个布尔值，Python 直接把它当字符串接了上去，于是 `False` 变成了 `false` 黏在模型名后面。
更麻烦的是这个错误不会报错，它只是安静地把一段脏文本塞进了上下文，模型该回答还是会回答，你根本发现不了。

**解决**：禁止裸拼接，全部改成具名占位符。

```python
SYSTEM = """你是学生的教务助手。
当前学生：{name}
运行模式：{mode}"""

prompt = SYSTEM.format(name=name, mode="离线规则" if offline else "在线模型")
```

顺手把模板单独抽到一个 `prompts.py` 里，让它可以被一眼看完、被单独检查。**提示词是不可测的代码，那就把它变得可读。**

## 坑二：把数据库会话塞进 LangGraph 的 State，然后炸了

**现象**：第一次对话正常，第二次对话抛异常，报的是序列化失败。

**原因**：我图省事，把 SQLAlchemy 的异步会话 `AsyncSession` 直接放进了 State：

```python
class AgentState(TypedDict, total=False):
    db: AsyncSession   # ← 灾难现场
    question: str
```

State 是要被 checkpoint 存下来的（我用了 `MemorySaver` 做多轮记忆）。而 `AsyncSession` 里挂着连接、事务、事件循环的引用，**它压根不可能被序列化**。记忆机制一生效，图就崩。

**解决**：State 只放能被序列化的纯数据，运行时对象走 `config`：

```python
await graph.ainvoke(
    {"question": q, "role": "student", "account": "2024010101"},
    config={
        "configurable": {
            "thread_id": f"student:2024010101:{session_id}",
            "db": db,          # 不进 state，不进 checkpoint
        }
    },
)
```

节点里用 `config["configurable"]["db"]` 取出来。这条规则后来被我当成了硬约束：**能进 State 的只有字符串、数字、字典、列表；连接、客户端、锁，一律走 config。**

附带好处是 `thread_id` 用「角色:账号:会话ID」拼出来，天然隔离了学生 A 和学生 B 的记忆，不会串台。

## 坑三：模型把「周三」抽成了字符串，工具直接抛异常

**现象**：学生问「这周三有什么课」，第一周能用，第二周开始报错。日志里显示传进工具的参数是 `weekday="周三"`。

**原因**：我在工具定义里写的是 `weekday: int`，指望模型抽成数字。模型有时候抽 3，有时候很贴心地抽成「周三」——它觉得自己在帮忙。

这还是小问题。真正难受的是另一个：学生问「我上学期高数多少分」，模型抽出来的课程名是「高数」，而数据库里叫「高等数学A(上)」，模糊匹配查不到，于是模型很自然地回答「没有查到你的成绩」——**它在撒谎，但流程完全成功**。

**解决**：两道防线。

第一道，参数进工具之前统一做类型收敛，「周三」→ 3，「3」→ 3，「上学期」→「2024-2025-1」：

```python
def coerce_int(v, default=None):
    if isinstance(v, int):
        return v
    if isinstance(v, str):
        m = re.search(r"\\d+", v)        # 从「周三」「第3周」里抠数字
        if m:
            return int(m.group())
    return default
```

第二道，查不到就**回退**：课程名精确匹配失败 → 去掉括号部分再匹配 → 再做包含匹配 → 都没有，才允许回答「没查到」，并且把「我按 XX 这个名字找的」一起告诉用户。

这一条是我觉得整个项目里最值钱的经验：**Agent 的 bug 大多数不是崩溃，是「流程成功但答案是错的」。** 所以验收的时候不能只看它有没有报错，得看它答得对不对。

## 坑四：聊到第十轮以后，明显变慢

**现象**：前几轮很顺，聊十轮之后每次回复要等十几秒，界面上那行「过程」越堆越长，一屏幕都放不下。

**原因**：我图好看，把每一轮的工具执行过程都塞回了上下文，包括「规划了什么 → 调了哪个工具 → 参数是什么 → 返回了什么」。这些内容只会累加，不会消失，二十轮之后单次请求的 token 直接翻几倍。

**解决**：分三件事。

1. **历史只留最近若干轮**，更早的折叠成一句摘要。
2. **执行过程只留在当轮返回给前端的 `trace` 字段里**，不写回对话历史——它是给人看的，不是给模型看的。
3. 工具返回**只给结论字段**，不要整段 JSON 全塞进去。

改完响应时间回到了稳定水平。这里踩的坑本质上是个反直觉的点：**上下文不是越多越好。给模型看的过程越长，它越容易被自己的历史带跑。**

## 坑五：教师端所有按钮都报 405 Method Not Allowed

**现象**：发通知、上传成绩 Excel，页面能打开，一点提交就红字报错，后端日志显示 `405 Method Not Allowed`。

**原因**：前端那几个请求写漏了 `method`，浏览器默认用 GET 发出去，而接口只接受 POST。后端没错，是前端请求发错了方法。

**解决**：把所有请求统一封装成一个函数，默认 POST，需要 GET 的地方显式声明：

```javascript
async function api(path, body) {
  const res = await fetch(path, {
    method: body === undefined ? "GET" : "POST",
    headers: { "Content-Type": "application/json" },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  if (!res.ok) throw new Error("请求失败：" + res.status);
  return res.json();
}
```

顺带还揪出一个亲兄弟：导出成绩时页面白屏，报 `Cannot read properties of undefined (reading 'avg_score')`。原因是后端返回的是带分页的对象 `{items: [...], total: n}`，前端当成数组直接取第一项的字段。**接口返回结构不统一，前端就会在某个犄角旮旯里白屏。**

## 一个额外的小彩蛋：部署时 pip 报 403

在云服务器上装依赖，`pip` 一直 403 Forbidden，看着像网络问题，其实是镜像源对某些版本做了拦截。换成国内镜像并加 `--trusted-host` 之后一次装完。这种事不会出现在教程里，但第一次上服务器的人一定会遇到。

## 回头看，值得留下的三条

1. **State 里只放能序列化的东西**，连接和会话走 `config`。这条不懂，checkpoint 迟早崩。
2. **Agent 的验收标准是「答案对不对」，不是「有没有报错」**。参数要收敛，查不到要回退，宁可多说一句「我按什么名字找的」。
3. **上下文要做减法**。历史留近几轮，过程只给前端看，工具只回结论。

整套系统最后是这么个形态：FastAPI 提供接口、SQLAlchemy 2.0 异步 ORM（本地 SQLite / 云端 PostgreSQL 一行配置切换）、LangGraph 四节点编排、双模型双 Key 分别服务学生和教师、RAG 兜底回答教务规章、LangSmith 记录链路。

学生端和教师端的工具清单是**两套独立的**——越权请求不是靠提示词拦住模型，而是那个工具压根不在它的清单里。这是我做权限时唯一觉得安心的设计。

另外，没有配大模型 Key 也能跑：系统会退到离线规则模式，功能一模一样，只是意图识别由规则引擎代劳。这个设计当初只是为了省钱，后来发现演示的时候特别救命——**网络不好也能讲完。**
